## Context

Механизмы подготовки host, запуска, backup и offline restore уже разделены между самостоятельными Bash-скриптами. Новый слой должен оркестрировать их без дублирования recovery-логики, сохранить bind-mounted state вне контейнера и учитывать, что официальный image работает как непривилегированный пользователь `node` с UID/GID `1000:1000`. Требования к наблюдаемому поведению описаны в `specs/portable-agent-deployment/spec.md`.

## Goals / Non-Goals

**Goals:**

- свести новый deployment и disaster recovery к заполнению `.env` и одной setup-команде;
- сохранить отдельные низкоуровневые скрипты идемпотентными и пригодными для диагностики;
- выполнять повседневные операции без root при совпадении UID deployment-пользователя и контейнера;
- исключить попадание master password restic в командную строку и shell history;
- не допустить автоматического запуска второго экземпляра с тем же Telegram token после restore.

**Non-Goals:**

- автоматическая установка ОС, создание deployment-пользователя или настройка SSH/firewall;
- хранение `.env` и recovery-секретов в Git либо restic backup;
- изменение формата штатного OpenClaw archive или структуры persistent state;
- публичная публикация Control UI, автоматический Telegram pairing или настройка nginx;
- замена существующих low-level команд backup, restore и host preparation.

## Decisions

### 1. Один оркестратор с явными режимами

`scripts/setup.sh` координирует существующие операции и принимает только `new` либо `restore [latest|SNAPSHOT_ID] [--force]`. Общие проверки выполняются до выбора ветки, а фактическое восстановление делегируется `restore.sh`.

Альтернатива — оставить в README последовательность ручных команд. Она отвергнута, потому что переносит порядок действий, загрузку `.env`, права и различие `restic init`/`restore` на оператора.

### 2. `.env` загружается внутри каждого проектного скрипта

Общая функция `load_env` экспортирует значения из project-local `.env`, а Docker Compose всегда получает тот же файл через `--env-file`. Оператору не требуется выполнять `source`, поэтому переменные не зависят от состояния интерактивной shell-сессии.

Альтернатива — требовать предварительный `export` всех переменных. Она создаёт трудно диагностируемое расхождение между restic, Compose и вызовами через `sudo`.

### 3. Повышение прав ограничено подготовкой host

Setup допускает root или текущий UID, равный `OPENCLAW_UID`. Для каждого управляемого дерева определяется ближайший существующий родитель: если он доступен для записи, подготовка идёт без root; иначе через `sudo` вызывается только `prepare-host.sh`. При root-вызове каталоги и файлы назначаются `OPENCLAW_UID:OPENCLAW_GID`, после чего restic, pull, start и restore продолжаются от deployment-пользователя.

Альтернатива — всегда запускать весь setup через `sudo`. Она проще, но оставляет runtime-файлы и Docker-операции зависимыми от root и воспроизводит проблему недоступного обычному пользователю password file.

### 4. Restic password хранится в отдельном защищённом файле

`prepare-host.sh` создаёт каталог secrets с mode `0700`, дважды читает пароль через скрытый интерактивный ввод и записывает обычный файл с mode `0600`. В режиме `new` ввод нужен при отсутствии файла; в режиме `restore` он запрашивается всегда, чтобы оператор явно использовал recovery-копию из password manager. Родитель password file проверяется против списка опасных слишком широких путей.

Альтернатива — передавать пароль через аргумент команды или создавать файл вручную. Аргумент раскрывает секрет в history/process list, а ручное создание снова требует отдельной настройки владельца и permissions.

### 5. Ветка `new` проверяет семантику repository

Сначала выполняется безопасная проверка restic config. Неинициализированный repository создаётся через `restic init`; уже инициализированный repository без snapshots `personal-agent` считается следом прерванного нового setup; наличие таких snapshots блокирует `new` и направляет к `restore`.

Альтернатива — безусловно выполнять `restic init`. Она некорректна для существующего backend и не отделяет новый экземпляр от recovery-сценария.

### 6. Restore остаётся offline до явного запуска

Ветка `restore` сначала подтверждает наличие snapshots агента и загружает закреплённый image, необходимый для verify/doctor. `restore.sh` проверяет, что Gateway остановлен, восстанавливает во временный staging, верифицирует штатный архив, сохраняет прежнее дерево в `pre-restore-*` и активирует данные. Оркестратор намеренно не вызывает `start.sh`.

Альтернатива — автоматически запустить Gateway после успешного doctor. Она создаёт риск одновременной работы двух Telegram/OpenClaw экземпляров при миграции.

### 7. Операторские обёртки не скрывают низкоуровневые команды

Make targets `setup-new`, `setup-restore` и `backup-list` повторяют основные сценарии, а `backup-maintenance.sh snapshots` централизует загрузку `.env` и фильтр `--tag personal-agent`. Прямые вызовы low-level скриптов сохраняются для диагностики и специальных операций.

## Risks / Trade-offs

- [Неверный пароль в режиме restore перезапишет локальный password file до проверки repository] → пароль остаётся в password manager; setup можно повторить с корректным значением, а live state до успешного доступа к snapshots не заменяется.
- [Проверка `restic cat config` не различает неинициализированный backend, сетевую ошибку и неверные credentials] → последующий `restic init` обязан завершиться ошибкой backend; setup не продолжает pull/start при ошибке.
- [Совпадение UID не гарантирует одинаковую локальную модель групп на всех host] → root-подготовка использует явный `OPENCLAW_UID:OPENCLAW_GID`, а rootless-сценарий документирует требование доступности каталогов и Docker daemon deployment-пользователю.
- [Вызов `sudo` исполняет скрипт из рабочей копии с повышенными правами] → репозиторий считается доверенной инфраструктурной конфигурацией, а повышение ограничено отдельным скриптом подготовки и проверенными абсолютными путями.
- [Restore с `--force` заменяет существующее состояние] → Gateway должен быть остановлен, предыдущее дерево перемещается в timestamped rollback-каталог, а новый state проходит offline `doctor`.

## Migration Plan

1. На существующих машинах сохранить текущий `.env`, restic master password и действующий persistent state; формат данных не меняется.
2. Для нового экземпляра после установки зависимостей запускать `./scripts/setup.sh new` вместо ручных `prepare-host`, `restic init`, `docker compose pull` и `start`.
3. Для переноса заполнить `.env` прежними credentials и выполнить `./scripts/setup.sh restore latest`; новый Gateway запускать только после остановки старого.
4. Проверить `healthcheck`, Telegram owner/pairing и создать новый off-site backup с новой машины.

При откате оператор может продолжить использовать сохранённые low-level скрипты. После принудительного restore предыдущее состояние доступно в `${PERSONAL_AGENT_BACKUP_DIR}/pre-restore-*` для ручного возврата на остановленном Gateway.
